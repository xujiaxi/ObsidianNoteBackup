# System Design 答题框架（45 分钟流程版）

> 来源：Day 1 讲解整理（2026-09-18）
> 配套：`plans/two-week-plan-2026-09-18.md`、`system-design/fundamentals.md`
> 用法：每道设计题的 `system-design/{theme}.md` 都按本文第 6 节的模板产出

## 1. 时间分配（把面试当流程走）

| 阶段 | 时间 | 你要做的事 | 千万不要做 |
|---|---|---|---|
| 需求澄清 | 0–5min | 问 5 个问题，然后**复述确认** | 上来就画框图 |
| 容量估算 | 5–10min | 算 QPS / 存储 / 带宽 / 机器数 | 说"规模不大不用算" |
| API + 数据模型 | 10–15min | 3–5 个端点 + 表结构 + 存储选型理由 | 写完整 SQL/Protobuf |
| 高层架构 | 15–30min | 组件 + 数据流（画图 + 口述请求路径） | 一上来就谈多机房 |
| 深挖 | 30–40min | 面试官指定，答"怎么做 + 为什么" | 只给结论不给取舍 |
| 收尾 | 40–45min | 失败模式、降级、演进路线、反问 | 说"设计完了"然后沉默 |

**核心原则**：前 15 分钟只动嘴不动笔。面试官打分里「是否先定义问题」权重很高。

## 2. 需求澄清五问（背熟）

1. **核心用户动作是什么**，谁是主要读方、谁是主要写方？
2. **规模**：DAU 多少、峰值 QPS、数据量级、数据保留多久？
3. **读写比例**多少？（决定推/拉、缓存策略、有序结构要不要预维护）
4. **一致性要求**：强一致还是最终一致？延迟 SLA 多少？（决定单主/多主/CRDT）
5. **边界**：多区域？移动端？合规（PII/支付）？成本约束？

收尾话术：「我理解这个系统需要支持 X 做 Y，规模是 Z，允许最终一致但延迟要在 W 以内——如果理解有偏差请纠正我。」

## 3. 容量估算速算手册

### 3.1 常数表（记这几个就够）

| 量 | 值 | 用途 |
|---|---|---|
| 一天 | ≈ 86,400s，**按 10^5 算** | 日均 → QPS |
| 一个月 | 2.6 × 10^6 s | |
| 一年 | 3.15 × 10^7 s ≈ 3 × 10^7 | 年存储 |
| 单机 Web 服务 | 1K–10K QPS | 应用层机器数 |
| 单实例 MySQL | 写 1K–10K TPS，索引读 10K QPS | 存储选型 |
| Redis 单实例 | 10^5 QPS | 缓存/榜单 |
| 单机内存 | 128–256 GB | 能不能全放内存 |
| SSD 随机 IOPS | 10K–100K | 是否需要 LSM 结构 |
| 可用性 | 99.9% = 8.76h/年；99.99% = 52.6min/年 | SLA 话术 |

### 3.2 公式链（按顺序算，别跳步）

```
日均请求   = DAU × 人均日操作数
平均 QPS   = 日均请求 / 10^5
峰值 QPS   = 平均 × 3   （社交/电商 3~5，内部工具 2）
日增存储   = 日请求 × 单条大小
年存储     = 日增 × 365 × 副本数(3) × 索引放大(1.5)
出带宽     = 峰值 QPS × 平均响应大小
机器数     = 峰值 QPS / 单机容量 ÷ 0.7（留余量）
缓存内存   = 热数据条数 × 单条大小（热数据通常取 20%）
```

### 3.3 演练 A：News Feed（200M DAU）

- 读：200M × 10 次/天 = 2B/天 → **20K QPS 平均，60K 峰值**
- 写：200M × 0.1 帖/天 = 20M/天 → 200 QPS → 峰值 600 QPS
- 读写比 **100:1** → 结论：重缓存 + 预生成 timeline（fanout on write），读路径不能碰 DB
- 存储：20M × 1KB = 20GB/天 → 7.3TB/年，×3 副本 ≈ 22TB
- 结论：应用机 ~60 台（按 1K QPS/台算 60K 峰值），Redis 存热 timeline：200M × 800 条 × 8B(post_id) ≈ 1.3TB → 分片 20 台

### 3.4 演练 B：视频上传（100M DAU，面经 5）

- 上传数：100M × 0.01 视频/天 = 1M 视频/天 → 12 QPS 平均，峰值 ~40 QPS
- 大小：1M × 200MB = **200TB/天** ← 一眼看出瓶颈在存储不在 QPS
- 年存储：200TB × 365 × 1.2（转码多码率）= 87PB → 对象存储 + 冷层
- 上传带宽：40 QPS × 200MB / 300s = **27GB/s** → 必须分片直传对象存储 + CDN 边缘接入，绝不过应用服务器
- 转码算力：1M 视频 × 5min = 5M 分钟素材/天；多码率 3 档 × 0.5x 实时速度 → 5M × 3 / 0.5 = 30M 机器分钟/天 = 20,833 机器小时 → 若每台 24h 跑满，**约 870 台转码机**（按 70% 利用率 ≈ 1250 台）

**这套算法就是面试官想听的**：不是背数字，而是从数字推出架构决策（「27GB/s 决定了不能过应用层」）。

## 4. 高层设计怎么讲（15 分钟）

1. 先画 4 层：客户端 → 接入层（LB/CDN）→ 服务层（无状态）→ 存储层（缓存/DB/对象存储/队列）
2. 然后**用一条请求路径串起来**：「用户发帖 → API 网关 → 帖子服务写主库 → 发消息到队列 → 扇出服务写 fanout → 读时直接读 Redis timeline」
3. 每个组件说一句选型理由，不要列产品名清单
4. 主动提一个「我先不做」的部分（如「v1 不做多区域，后面演进再加」）→ 显示边界感

## 5. 深挖与失败模式（面试官最爱的三连）

- **数据一致性**：写扩散怎么保证不丢帖？（outbox/队列 + 幂等 + 重试）
- **热点**：明星用户/爆款帖子怎么办？（拉模式兜底 + 本地缓存 + 请求合并）
- **降级**：Redis 挂了读什么？（降级直连 DB + 限流 + 返回陈旧数据）
- **扩缩容**：分片键怎么选？扩分片怎么迁数据？（一致性哈希 / 预分片）
- **可观测性**：出问题怎么定位？（埋点 + 尾延迟 + 队列堆积告警）

## 6. 每份设计文档的统一模板

```
## 需求澄清（功能 / 非功能 / 规模假设）
## 容量估算（QPS、存储、带宽、机器数）
## API 设计
## 数据模型与存储选型（含"为什么不是另一个"）
## 高层架构（组件 + 数据流）
## 深挖点（3 个，每个 5 分钟）
## 失败模式与降级
## 演进路线（v1 → v2）
```
